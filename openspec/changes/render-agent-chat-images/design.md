## Context

`SimulationResponse` 与测试评估聊天已经支持 `image_url`，公共 `RuntimeMessageContent` 也能够解析相对 API 地址并渲染图片。构建页右侧实时预览仍使用独立的纯文本映射和消息气泡，因此后端生成图片时字段在状态写入阶段被丢弃。

本次修改需要保持 Live 数据真实透传，不引入前端伪图片，也不能新增另一套 URL 解析逻辑。

## Goals / Non-Goals

**Goals:**

- 构建预览保留模拟响应中的图片与已有富媒体字段。
- 所有 Agent 预览入口复用相同的富媒体消息渲染规则。
- 相对 `/api/v1/files/...` 地址根据公共 API base 正确解析。
- 用自动测试覆盖字段映射与图片地址解析。

**Non-Goals:**

- 不改变图片生成接口、下载接口或认证方式。
- 不增加图片画廊、编辑、下载鉴权代理或加载进度能力。
- 不改变消息气泡整体视觉结构。

## Decisions

1. **复用 `RuntimeMessageContent`**
   - 构建预览把 `TestMessage` 的文本、附件、音频、文档和图片字段交给公共组件。
   - 未选择在构建预览内单独渲染 `<Image>`，避免地址解析、可访问性和样式分叉。

2. **在响应映射阶段完整保留已有富媒体字段**
   - 将 `attachments`、`audio_url`、`docx_url` 和 `image_url` 一并写入预览消息。
   - 虽然本次缺陷只暴露了图片字段，但完整映射可与测试评估入口保持一致，并避免同类字段继续丢失。

3. **保持相对地址解析规则**
   - 以 `/` 开头的地址拼接 `getApiBaseUrl()`；绝对地址原样使用。
   - 示例响应 `/api/v1/files/.../download` 将解析为当前后端地址，不重复追加 `/api/v1`。

## Risks / Trade-offs

- [生成图片尺寸差异可能让消息高度增加] → 继续使用公共组件的最大高度和裁切规则，点击图片可打开原图。
- [图片下载端点若要求浏览器无法携带的自定义请求头，直接图片请求可能失败] → 当前文件下载 URL 是后端可直接访问契约；若后端改为强制 `X-API-Key`，需另行设计鉴权代理，不在本次范围内。
- [公共组件变更影响多个聊天入口] → 本次不修改公共组件展示逻辑，只复用既有能力并补测试。
